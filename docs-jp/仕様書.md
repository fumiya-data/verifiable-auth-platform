## 1. 目的

Verifiable Auth Platform は、検証可能性を中核特性とするローカル認証基盤です。
単に認証機能が存在することではなく、その振る舞いが一貫した形で仕様化され、
実装され、テストされ、観測され、分析され得ることを要求します。

プラットフォームは 4 層で構成されます。

- 形式仕様層 (`Lean`)
- 実装層 (`C`)
- 運用層 (`Go` TUI)
- 観測・分析層 (`observability` と `Python`)

対象領域は単一ノード上のパスワード認証です。次は明示的に対象外です。

- 分散認証
- 多要素認証
- 外部 ID 連携

## 2. 範囲と前提

### 2.1 範囲

本システムは、単一ノードのパスワード認証ワークフローに対して、アカウント登録、
ログイン、パスワード変更、ログアウト、監査確認、メトリクス確認を提供します。

### 2.2 前提

- 実行環境はローカルであり、単一プロセスまたは単一ノードに制約されます。
- 認証は `login_id + password` に基づきます。
- パスワードは平文で保存されません。
- ハッシュ関数は決定的関数として扱います。
- 各ユーザーごとに独立した一意の salt を生成します。
- 認証状態は単一セッション `Option<LoginId>` で表されます。
- TUI は engine の公開契約だけを利用し、認証ロジックを持ちません。
- 観測・分析層は読み取り専用であり、認証状態を変更してはいけません。

## 3. システムモデル

システムは状態遷移系として定義されます。

### 3.1 状態

```text
State:
  users: List<User>
  authenticated: Option<LoginId>
```

### 3.2 ユーザー

```text
User:
  login_id
  salt
  password_hash
  failed_attempts
  lock_state
```

### 3.3 操作

システムは次の状態遷移操作を公開します。

- `register(id, password)`
- `login(id, password)`
- `change_password(old, new)`
- `logout`

## 4. 中核不変条件

以下の不変条件が、プラットフォームに求められる安全性と整合性を定義します。

- `I-01`: パスワード平文は状態・ログ・出力に一切現れてはならない。
- `I-02`: `login_id` は一意でなければならない。
- `I-03`: `password_hash = hash(password, salt)` が常に成り立たなければならない。
- `I-04`: `failed_attempts >= 0`。
- `I-05`: `failed_attempts >= threshold` なら `lock_state = Locked`。
- `I-06`: `lock_state = Locked` のとき成功ログインは不可能。
- `I-07`: ログイン成功時は `failed_attempts = 0`。
- `I-08`: 登録成功時、新規ユーザーは `failed_attempts = 0` かつ `lock_state = Active`。
- `I-09`: パスワード変更成功時、salt と hash は新たに導出された値へ置換されなければならない。
- `I-10`: `logout` は `users` を変更してはならない。
- `I-11`: 認証状態は `Unauthenticated` または `Authenticated` のいずれかである。
- `I-12`: 仕様が明示的に更新を許可する場合を除き、失敗した操作は状態を変更してはならない。
- `I-13`: `WellFormed(state)` はすべての操作で保存されなければならない。
- `I-14`: 形式仕様、engine、tests、observability model は整合していなければならない。

## 5. 操作意味論

### 5.1 Register

#### 前提条件

- 指定された `login_id` がまだ登録されていないこと。

#### 遷移

```text
salt <- freshSalt
hash <- hash(password, salt)
user <- mkUser(id, salt, hash)
users <- insert(user)
```

#### 結果

- `success`
- `duplicate`

#### 性質

- 認証状態は変化しない。
- 新規ユーザーは `lock_state = Active` で初期化される。
- 新規ユーザーは `failed_attempts = 0` で初期化される。

### 5.2 Login

#### 分岐

1. ユーザーが存在しない
   - 結果: `unknown_user`
   - 状態: 変更なし

2. ユーザーがロックされている
   - 結果: `locked_out`
   - 状態: 変更なし

3. パスワードハッシュが一致しない
   - `failed_attempts <- failed_attempts + 1`
   - threshold 未到達:
     - 結果: `wrong_password`
   - threshold 到達:
     - `lock_state <- Locked`
     - 結果: `locked_out`

4. パスワードハッシュが一致する
   - `failed_attempts <- 0`
   - `authenticated <- some id`
   - 結果: `success`

#### 性質

- 認証状態を変更できるのは `success` だけである。
- 失敗時、`authenticated` は変更されない。
- `locked_out` は「すでにロック済み」または「今回の失敗で新規ロックされた」の両方を意味し得る。
- `authenticated = some other_id` のとき `id` としてのログインは `already_authenticated` で失敗し、状態は変わらない。
- `authenticated = some id` のとき、同じユーザーでの再ログインも `already_authenticated` で失敗し、状態は変わらない。

### 5.3 Change Password

#### 前提条件

- `authenticated = some id`

#### 分岐

1. 認証済みセッションがない
   - 結果: `unauthorized`
   - 状態: 変更なし

2. 認証済みなのに対応ユーザーレコードがない
   - 結果: `system_error`
   - 解釈: 整合性違反

3. 旧パスワードが一致しない
   - 結果: `wrong_password`
   - 状態: 変更なし

4. 旧パスワードが一致する
   - `salt <- freshSalt`
   - `hash <- hash(new, salt)`
   - `user <- rehashUser`
   - `failed_attempts <- 0`
   - `lock_state <- Active`
   - 結果: `success`

#### 性質

- 認証済みセッションは保持される。
- パスワード変更成功時は、以前のロック状態も解除される。
- `change_password(old, new)` は現在認証されているユーザーにのみ適用される。

### 5.4 Register While Authenticated

`authenticated = some id` のときでも `register(new_id, password)` は有効であり、
認証状態は変更されない。

### 5.5 Logout

#### 遷移

```text
authenticated <- none
```

#### 結果

- `success`

#### 性質

- `users` は変更されない。

## 6. 状態遷移

### 6.1 アカウント状態

```text
Unregistered -> Active
Active -> Locked
Locked -> Active    (via change_password)
```

### 6.2 セッション状態

```text
Unauthenticated -> Authenticated
Authenticated -> Unauthenticated
```

## 7. データモデル

### 7.1 ユーザーレコード

```text
UserRecord:
  login_id          (unique)
  salt
  password_hash
  failed_attempts   >= 0
  lock_state        in {Active, Locked}
```

### 7.2 グローバル状態

```text
State:
  users: List<User>
  authenticated: Option<LoginId>
```

### 7.3 監査イベント

```text
AuditEvent:
  event_type in {
    Register,
    LoginSuccess,
    LoginFailure,
    Lock,
    PasswordChange,
    Logout
  }
  timestamp
  login_id
  result
```

### 7.4 メトリクス

```text
Metric:
  login_success_count
  login_failure_count
  lockout_count
```

### 7.5 観測可能性マッピング

- `register -> success` は `event_type = Register`, `result = success` を記録し、ログインメトリクスは変更しない。
- `register -> duplicate` は `event_type = Register`, `result = duplicate` を記録し、ログインメトリクスは変更しない。
- `login -> success` は `event_type = LoginSuccess`, `result = success` を記録し、`login_success_count` を増やす。
- `login -> wrong_password` は `event_type = LoginFailure`, `result = wrong_password` を記録し、`login_failure_count` を増やす。
- `login -> unknown_user` は `event_type = LoginFailure`, `result = unknown_user` を記録し、`login_failure_count` を増やす。
- `login -> locked_out` は、新規ロックアウトを引き起こした場合に `event_type = Lock`、すでにロック済みだった場合に `event_type = LoginFailure` を記録する。どちらの場合も `result = locked_out` であり、`login_failure_count` は増え、新規ロックアウト時のみ `lockout_count` が増える。
- `login -> already_authenticated` は `event_type = LoginFailure`, `result = already_authenticated` を記録するが、ログインメトリクスは変更しない。
- `change_password -> success` は `event_type = PasswordChange`, `result = success` を記録し、ログインメトリクスは変更しない。
- `change_password -> wrong_password | unauthorized | system_error` は対応する `result` を持つ `event_type = PasswordChange` を記録し、ログインメトリクスは変更しない。
- `logout -> success` は `event_type = Logout`, `result = success` を記録し、ログインメトリクスは変更しない。

## 8. システムアーキテクチャ

```text
spec (Lean)
  -> defines
engine (C)
  -> exposes CLI contract
tui (Go Bubble Tea)
  -> interacts via contract
observability (logs and metrics schema)
  -> consumed by
analysis (Python)
```

### 各層の責務

- `spec`: 不変条件と操作意味論を定義する
- `engine`: 状態遷移を実装する
- `tui`: 運用上のインターフェースを提供する
- `observability`: 監査とメトリクスの記録モデルを定義する
- `analysis`: 記録された振る舞いを可視化・集計する

## 9. インターフェース契約

engine は次の CLI コマンドを公開しなければなりません。

- `register`
- `login`
- `change-password`
- `logout`
- `show-audit`
- `show-metrics`

すべての出力は機械可読であり、JSON として直列化されなければなりません。

CLI 契約は次で構成されます。

- 安定したコマンド名
- 安定した JSON 応答フィールド名
- 安定した result code
- 同値な結果に対する決定的な直列化

すべてのコマンド応答は次を含まなければなりません。

- `ok: boolean`
- `result: string`
- `data: object | null`
- `error: object | null`

`ok = true` なら `error = null` です。

`ok = false` の場合でも `result` は安定した機械可読コードを保持し、
`error` は秘密情報を漏らさず失敗内容を説明しなければなりません。

TUI が利用してよいのは engine 契約だけです。認証ルールを埋め込んだり、
業務ロジックを複製したりしてはいけません。

## 10. テスト戦略

### 10.1 テスト種別

- 仕様整合性のための契約テスト
- engine 内部の unit test
- storage と CLI 挙動の integration test
- TUI 相互作用の end-to-end test
- 出力固定化のための golden test

### 10.2 トレーサビリティ規則

- 形式モデルで指定した各ケースは、少なくとも 1 つの契約テストに対応しなければならない。
- CLI 出力は、適切な箇所で golden file により安定化しなければならない。

## 11. 観測可能性

### 11.1 記録対象

- イベント列としての監査ログ
- 集計カウンタとしてのメトリクス

### 11.2 制約

- 秘密情報はログやメトリクスに一切含めてはならない。
- 記録された振る舞いは追跡可能でなければならない。
- 記録された振る舞いは分析可能な形で再現できなければならない。

## 12. 分析

Python の分析層は次に利用できます。

- 監査集計
- 失敗分布分析
- ロックアウト発生分析
- テスト結果の可視化

### 分析層の制約

- 分析層は厳密に読み取り専用である。
- 分析層は認証状態を変更してはならない。

## 14. 命名規約

- リポジトリ名、文書名、JSON ファイル名: `kebab-case`
- C の識別子とファイル名: `snake_case`
- Go の package 名: `lowercase`
- Go のファイル名: `snake_case`
- Python の module 名とファイル名: `snake_case`
- Lean の module 名と type 名: `PascalCase`

## 15. エッジケース

- `threshold = 0` は禁止する。
- `unknown_user` と `wrong_password` を区別表示するかどうかは UI レベルの方針である。
- 空パスワードを許可するか禁止するかは仕様で明示しなければならない。
- storage corruption は `system_error` にしなければならない。

## 16. 失敗モード

次のアーキテクチャ上の失敗は積極的に防止されなければなりません。

- 形式仕様と engine の乖離
- TUI への認証ロジック流入
- 観測可能性が無構造ログへ劣化すること
- 分析層内で認証ロジックを再実装すること
- `WellFormed(state)` が弱まり、整合性が崩壊すること
- CLI 契約の不安定さによる UI 破損

## 17. 検証目標

本プラットフォームの目的は、単に認証機能を提供することではありません。
次を満たす認証実装基盤を確立することです。

- 仕様が明示的である
- 実装が仕様に従う
- テストが仕様を検証する
- ログと分析が振る舞いを追跡可能にする

したがって:

```text
verifiable-auth-platform = a verifiable implementation foundation for authentication state transitions
```
